# SQLite 实施修订

日期：2026-10-08（Asia/Shanghai）。用户已确认将首版数据库从 PostgreSQL 改为 SQLite。

本文覆盖 v2.0 主设计中的 PostgreSQL 专属实现。会话终态、不可变原始字节、精确接收与封存凭证、单写者许可、调度及文件生命周期合同继续适用。数据库换型不表示这些业务功能已经完成。

运行架构按[轻量化架构与并发稳定性决策](轻量化架构与并发稳定性决策.md)修订：业务写入移到单个专职 DB worker，有界排队及单在途 RPC；不默认跨请求组提交。本文的单视图导出和联合备份流程继续适用，不能把 Online Backup 变成所有导出的强制前置。

## 1. 当前选择

首版使用一个 Node.js/Fastify 应用和一个 SQLite 数据库文件，驱动为 `better-sqlite3`。具体依赖固定在 `package.json` 和 `package-lock.json`；运行检查页报告实际 SQLite 引擎版本。数据库放在本机持久磁盘，研究图片、导出和备份仍使用三个私有逻辑存储区。

选择依据是当前单机、小规模采集和单个主要研究者的使用方式。20 人同时参与是后续验收目标，不能由数据库名称推断已经达标。若实测短事务吞吐或延迟不足，再评估回到 PostgreSQL。

数据库连接统一启用 `journal_mode=WAL`、`synchronous=FULL`、`foreign_keys=ON` 和有限 `busy_timeout`。macOS 开发机同时启用 `fullfsync`、`checkpoint_fullfsync`。设置必须检查实际返回值，不能静默回退到其他日志模式。最低引擎版本为 3.51.3，避免已公开的 WAL-reset 缺陷；后续升级继续保留实际版本和故障回归记录。依据：[SQLite WAL](https://www.sqlite.org/wal.html)、[同步设置](https://www.sqlite.org/pragma.html#pragma_synchronous)。

WAL 支持读写并行，但同一时刻只有一个写事务。活跃数据库、WAL 和共享内存文件在同一主机的本地文件系统；NAS 可以作为完成后备份的独立目的地，不能用来承载活跃 WAL 数据库。[SQLite 隔离说明](https://www.sqlite.org/isolation.html)

## 2. 写入与接收凭证

业务写入使用短 `BEGIN IMMEDIATE` 事务。唯一约束、原始正文、摘要、接收身份、当前处置和相应投影在同一事务内处理，提交成功后才返回 ACK。事务内禁止网络请求、图片解码、文件复制和长时间计算；不在同步事务回调中使用 `await`。

PostgreSQL 的 `SELECT ... FOR UPDATE`、序列、JSONB、数组列、占位符及 advisory lock 不能直接搬用。实施时用 SQLite 唯一索引、外键、CHECK、STRICT 表及事务内条件更新实现同等业务约束。原始事件用 BLOB 保存一次编码后的精确 UTF-8 字节；查询用解析字段另存，不以 JSON 重编码替代原始正文。

单写者 fence、未关闭 permit 的独占、接入暂停检查和分配一次核销仍在事务中核对。`SQLITE_BUSY`、磁盘满、I/O 错误或未知提交不能返回成功，也不能给同一逻辑请求生成新身份。浏览器继续保留原始副本，按原身份补传或查询接收凭证。

`better-sqlite3` 的调用是同步的。正式业务由单个专职 DB worker 持有读写连接，HTTP 主线程使用按请求数／字节有界的队列，一次只发送一个在途 RPC。短事务内重新核验授权、fence、permit 和状态；首版一请求一事务，不默认跨请求 Group Commit。采集事务必须有实测的时间与条数预算；导出、深度对账和维护工作一次一个，在受限维护 worker 中执行。worker 仍竞争 CPU／磁盘，不承诺零阻塞。P0 已将健康查询和测试业务一起移到单 DB worker，接收及 RPC 队列均有数量/字节上限；细节见《P0实施与验收》。

未发送到 writer 的请求可明确为 NOT_INGESTED；已发送但超时／失联的请求是 UNKNOWN，按原身份查询／补传。未确认旧 worker 退出不得创建替代 writer，重启后凭持久接收状态消解未知提交。SQLite 写锁不替代浏览器单写者协议，也不自动保证只有一个应用写者。

## 3. 导出一致视图

替换 PostgreSQL `REPEATABLE READ` 的路径为：在专用只读连接显式 `BEGIN`，执行第一次实际读取建立 SQLite 快照，然后在同一连接、同一事务内有界物化全部导出表和清单。记录实际读视图获取点、源集合摘要、软件 `snapshot_id` 与算法版本；`BEGIN` 时间和 WAL 文件名都不充当精确数据集合。[SQLite snapshot isolation](https://www.sqlite.org/isolation.html)

完成物化与集合核对后结束事务，再压缩和发布。长读事务会阻碍 WAL 回收，因此必须限制读视图时间、暂存容量和输出规模，并监测 WAL 大小。超限明确失败或生成各有独立 snapshot 的分范围包，不混合不同读视图。

## 4. 数据库与资源联合备份

SQLite 没有原设计的 `pg_export_snapshot`／`pg_dump --snapshot` 配对入口。新的备份路径如下，已在 lab_* 业务表实现并通过本机备份/恢复核查，独立目标仍待环境验收：

1. 持久登记备份作业，取得应用统一执行的资源生命周期屏障。屏障阻止资源发布、引用变更和维护删除；已有会话原始事件采集可以继续。任何会创建新资源引用的操作须遵守屏障。
2. 使用 SQLite Online Backup API 将数据库备份到私有暂存文件。等待 API 完整成功，重新打开备份文件并执行完整性检查；进行中的目的文件不提供恢复或下载。[官方备份 API](https://www.sqlite.org/backup.html)、[驱动 backup 方法](https://github.com/WiseLibs/better-sqlite3/blob/master/docs/api.md#backupdestination-options---promise)
3. 从**已完成的备份数据库**读取该恢复视图要求的完整资源清单，而不是从此刻的活跃数据库读取另一份清单。在屏障仍持有时，为这些对象在活跃数据库的短写事务中登记持久 BACKUP_PIN，核验真实对象可用、非删除状态，提交后再释放屏障。
4. 依据备份数据库清单复制不可变资源真实字节、冻结协议、运行器及恢复配置。独立目标完成摘要和引用核对后才能登记 READY；恢复演练另记结果。
5. 未完成作业、屏障和 pin 必须可恢复，不按租约时间直接释放。已经复制的数据库和资产不修改。备份里的作业状态不被解释为可直接恢复采集，恢复工具需处理未决维护状态。

在线备份的恢复点以成功完成的目的数据库内容为准，不冒充开始请求的时间点。备份前后的业务事件差异可以由该恢复视图如实解释；资源生命周期屏障确保视图需要的对象在 pin 建立前不会消失。

不得在数据库活动时只复制 `.sqlite` 主文件，遗漏 WAL 中的已提交内容。`research-backups` 当前仅是开发机目录，不是独立灾备副本；独立目标、频率、保留、RPO/RTO 与联合恢复仍属采集准入项。
