# 图片、文字、反馈与伪随机配置

上传 [randomized-stimuli.json](../examples/questionnaires/randomized-stimuli.json) 和 [mobile-stimuli.zip](../examples/stimuli/mobile-stimuli.zip) 即可试用。示例包含图片、文字、F/J 键、分类顺序、一般时长与题目覆盖。此示例是 TEST_ONLY；正式采集仍需既有环境验收及发布流程。

## 时长和 jitter

顶层 `timing_defaults` 为 general 设置，各组也可设置同名字段覆盖某一阶段。优先级为 **题目 > 组 > 顶层**，各阶段分别继承。

```json
"timing_defaults": {
  "stimulus_ms": "3+-0.5",
  "isi_ms": {"base": 800, "jitter": 200},
  "feedback_ms": 400
}
```

数字及 `{base,jitter}` 的单位为毫秒；`"3+-0.5"` 或 `"3±0.5"` 的单位为秒，表示 2.5–3.5 秒。字符串须有引号，不支持算式求值。刺激下限至少 1ms，ISI/反馈下限可以为 0，每阶段上限 60 秒，整组仍受总时长预算约束。

一般设置针对**每个参加者、每个组、每个阶段的原始试次**独立平衡。N 个适用试次在区间内取对称等距时长，随后使用该参加者的随机种子打乱。例如 `3±0.5`、N=5 时，时长集合为 2.5、2.75、3、3.25、3.5 秒，均值为 3 秒；N=1 时取 3 秒。不会依赖多个参加者之间的平均来弥补某个人的不平衡。各组使用相同基准时，各组平衡也保证合并后的请求均值；各组覆盖基准时按各组各自设计执行。

题目可以指定自己的时长：

```json
{
  "root_id": "word-1",
  "text": "请选择左边",
  "correct": "左边",
  "timing": {"stimulus_ms": 1800, "isi_ms": "0.8+-0.2"}
}
```

此题刺激固定 1800ms、ISI 在 600–1000ms 内独立伪随机取值，这两个阶段不参与 general 平衡；未覆盖的反馈阶段仍继承一般设置。旧字段 `image_ms`（图片或文字的刺激时长）、`isi_ms`、`feedback_ms` 也可写数字或上述 jitter 形式。通常选 `timing` 或旧字段中的一种即可，不要重复定义。将既有 JSON 迁移到 general 平衡时，需删除题目原有的显式时长，否则它们仍作为题目覆盖。

浏览器实际呈现按测得帧周期向上取整。因此严格平衡的是**请求时长**，量化后的计划时长每阶段可增加不足一帧，不保证物理显示均值恰好等于基准。帧延迟继续记录与审核。补测试次 `repeats` 复用对应原始试次的已实现时长，不进入平衡池；补测会改变总时长与已呈现的类别序列。要求完整序列严格符合平衡设计时使用 `repeats: 0`。

## 刺激顺序

在组中设置 `ordering`：

| 设置 | 行为 |
| --- | --- |
| `{"mode":"fixed"}` | 固定顺序；缺省也是此模式 |
| `{"mode":"shuffle"}` | 以单个图片或文字试次为单位无放回洗牌 |
| `{"mode":"category"}` | 打乱类别块顺序，并打乱各类别内的试次 |
| `{"mode":"balanced","max_run":2}` | 按类别交错，同类别连续出现不超过 2 次；缺省为 1 |

后两种模式要求所有试次设置 `category`，如 `"positive"`、`"negative"`。每个 `root_id` 原始呈现一次，保留 JSON 定义的类别数量；想要各类数量相等，需要在 JSON 中提供相同数量。此处的平衡是受连续次数约束的随机排列，不会凭空复制题目，也不保证所有合法排列等概率、或类别×时长的交叉平衡。

无法满足的组合在导入时拒绝，例如 9 个 A、1 个 B 且 `max_run: 2`。调整试次数或 `max_run` 后重试，不会静默放宽限制。固定顺序遵循分配到的 `variants[].trial_order`；省略 variants 时就是 JSON 的数组顺序。其他模式在该顺序上生成该参加者的固定计划。

## 输入与反馈

试次使用 `image` 引用 ZIP 内图片，或使用 `text` 给出最多 200 个 UTF-16 单元的纯文字，二者只能选一个；内部 `study-v1` 图片用 `asset_id`。`correct` 为某个选项，或 `null` 表示不判断正误。

`response_keys` 按选项文字映射物理按键，例如 `{"左边":"KeyF","右边":"KeyJ"}`。配置时每个选项需要一个不同的键。支持字母、数字、方向键、Space 和 Enter。未配置时使用屏幕按钮。匹配按键阻止浏览器默认动作，忽略重复 keydown 与组合快捷键。

点击或按键后，按钮立即高亮，并提示“已记录”。仅第一次有效作答决定答案，随后点击不会覆盖；也不会因提前作答而提前换题。时序固定为 **刺激 → 反馈 → ISI 空屏**，总时长是三者之和。只有刺激窗口接受作答；ISI/反馈期的按压不会回答下一题，必须松开再按。任务区域禁止右键菜单、长按选择和拖动，右键/中键不计为作答。

设置大于零的 `feedback_ms` 和组级 `feedback` 即显示反馈：

```json
"feedback": {"correct":"正确", "incorrect":"错误", "miss":"未作答", "neutral":"已记录"}
```

反馈在刺激结束后显示，最长 100 个 UTF-16 单元；`correct: null` 使用 neutral。未配置文案则该阶段保持空屏；未配置反馈时长则时长为 0。作答即时高亮不属于此额外反馈阶段，不增加任何时间。

管理端“模拟”保留手动上一题/下一题，用于检查文字、图片和选项；计时、随机化、反馈及最终数据以发布后的 TEST_ONLY 参加者流程为准。修改 JSON 后需重新上传并发布新版本，历史冻结版本不会自动应用新配置。

## 可复现性与实现取舍

服务端签发组 permit 时生成种子及全部原始试次的顺序、时长，前端执行固定计划，任务内不发网络请求。permit 中 `plan.seed`、`plan.design.algorithm`、`requested`、`balanced_pools` 和量化后的 `roots` 可用于复查；本地记录和服务端回放仍校验输入、时序与封存。旧版固定时长/图片协议保持原序列化字段形状。

已通过 Gemini bridge 讨论设计，保留 [原始答复](gemini前端讨论/stimulus-design-response.md)。采用其服务端生成计划、零和 jitter、首答保护和统一输入审核建议。实现使用项目已有 Xoshiro128；不采用建议中的静默放宽类别约束，也不在作答时替换刺激。反馈使用独立固定阶段，避免受反应时影响。JSON 最终字段以本文为准。

运行 `npm run test:runner` 可测试真实页面、Canvas 图片/文字、触控与键盘、IndexedDB 记录、SQLite 存储、回放及封存。该测试用接口适配层连接实际 LabStore，绕开 Windows 不具备的 POSIX 私有目录权限检查；它不替代生产 HTTP/文件服务和真实手机验收。
