# 阿里云 1Mbps 部署与验证

2026-10-08。用户选择阿里云 Ubuntu 26.04、系统盘 2120 IOPS / 106.0 MB/s，以 1Mbps 公网带宽运行，原 2c4g 正在评估降至 1c2g。最新需求为整个参加者会话同时 1–2 例，其余 FIFO 等待，配置与占位规则见 [会话排队与小规格部署](会话排队与小规格部署.md)。此处记录已实施代码和本机证据；目标 ECS、真实设备与独立恢复尚未验收，正式 gate 保持关闭。

## 当前实现

| 环节 | 已实施行为 |
| --- | --- |
| 整例准入 | `SESSION_CONCURRENCY=2` 默认双例，可设为 1；SQLite 持久 FIFO 最多 64 个活动/等待条目；等待页不显示问卷，服务端同时门控任务开始与封存 |
| 整例回收 | 完成/明确终止释放；无 ISSUED 的失联 5 分钟回收，有效租约内刷新保持序位，主动退出后重排队尾；ISSUED 跨租约/重启占位；队首约 3 秒、其他约 10 秒查询，活动每分钟续租并合并写入 |
| 组前准备 | 全局 FIFO 最多 64 个票据，`PREPARATION_CONCURRENCY=1`；每个活动会话最多一个图片流；下载、摘要核验和解码串行 |
| 进度与取消 | 显示队列位置、原图字节进度；可取消；队首约 1 秒、其余约 5 秒轮询并增加随机抖动；活动准备每 20 秒续票；原方案/写者每分钟续期 |
| 实际流生命周期 | 持有名额至 HTTP finish/close 或文件错误；取消销毁文件流与响应，等待真实退出后再放行；精确票据 nonce 防止迟到释放影响新准备 |
| 有限预算 | 最多排队 45 分钟、本组准备 20 分钟、图片 60 秒无进展失败；票据闲置 90 秒清理，活动准备硬期限 20 分钟；每图至多 8 MiB 压缩工作缓冲，全部本组解码预算仍按冻结协议 |
| 采集合同 | 计时组内停止图片下载、准备轮询和会话续租，在途请求先结束；许可负责占位；无 Redis/集群，SQLite WAL/FULL、单 writer、精确原始字节/摘要、补传与封存不变 |
| 明确过载 | JSON/图片仅对明确 429/503 做有限同身份重试；未知网络错误不自动换身份重试；普通 API 总预算 60 秒，维护/组封存 180 秒 |
| 冻结运行器 | 构建时生成 gzip/br，留存后核对解压结果与 canonical 原代码摘要；按 Accept-Encoding 协商，完全拒绝时 406；重启跳过一致文件的重复写入；新归档文件 0600 |
| 旧版本升级 | 新构建的队列能力声明参与 runnerHash；旧冻结代码/摘要不改。旧图片 GET 保留原鉴权和原字节，加入同一 FIFO；新版本缺票据不能绕过准备门控 |
| 能力读取 | 只在原鉴权完成后读取归档；验证 canonical 摘要与声明；同摘要并发读取合并，最多 16 个不同摘要同时读取、完成缓存最多 64 项，失败不缓存；未知/损坏声明拒绝 |
| 服务模板 | 2c4g 模板 `MemoryMax=1536M`、`UV_THREADPOOL_SIZE=2`；1c2g 可选 drop-in 1024M/1 为待测起点；nginx 75 秒 keepalive，私有流不缓存/转码/压缩，公共 gzip/br 由 Fastify 发送；单应用/单维护 worker |

图片准备票据只在内存中，重启或票据失效后重新准备；整例准入 FIFO 存在 SQLite 中，恢复时保留有效序位并清理已过期且无 ISSUED 的条目。排队不会扩大带宽，也不限制管理预览、公共代码、导出/备份等所有服务流量。图片保持原字节与版本摘要；本轮没有在线转码、跨会话持久浏览器图片缓存或原始表改写。

旧客户端 20 秒准备超时仍然有效，服务端等待名额最多 18 秒。兼容保障旧请求合同和原身份，不能使旧代码获得新准备页的 45 分钟排队/20 分钟下载预算。低带宽研究应发布新版本用于后续新会话；既有会话继续保留旧冻结版本及记录。

## 带宽规划

1Mbps = 1000000 bit/s = 125000 B/s。若 N 个参加者都需要 S 字节唯一原图，总图片数据理想下限为 `N × S / 125000` 秒；还需加代码冷加载、轮询/API、TLS、网络损耗、解码和放行间隙。下表是集中到达 20 人的总下载量，不代表 20 例同时活动；整例等待还取决于每例问卷与任务时长。

| 20 人每人一组原图 | 图片正文理想下限 | 按 70% 带宽用于图片的规划假设 |
| --- | --- | --- |
| 1 MiB | 167.8 秒（2.8 分钟） | 约 240 秒（4 分钟） |
| 5 MiB | 838.9 秒（14 分钟） | 约 1198 秒（20 分钟） |

70% 是规划假设，未在 ECS 测量；实际每组图片总量尚未提供。准入应根据代表性研究的最大组、冷热加载和后台工作实测，超过等待预算时减少集中进入人数或拆分安全的组前批次。拆组需要新冻结版本，不能改动正在运行的任务。CPU/磁盘峰值与 fsync 尾延迟仍需分别测量，系统盘规格不能代替这些证据。

## 本机验证

使用 macOS arm64 / Apple M4 / Node 24.21.0，全部临时库和私有目录隔离。

- `npm run check`：类型、构建/预压缩、SQLite smoke、52 项单元/故障测试和 19 项 Chromium 测试；完整结果同步至 [P1–P6 实施记录](P1-P6实施与验收.md)。
- 真实 HTTP 单 writer 升级回归：关闭旧 writer 后启动新 writer 并发布新版本，旧 frozen row/ref 原样保留；旧 GET 原图摘要一致，新 GET 缺票据 409，错 Cookie 401；旧 GET 等待/取消与新票据共享容量。注入真实文件流错误后响应立即销毁，close 回收容量，后续 GET 成功。
- 冷缓存 20 个同摘要能力读取只读取 release/contract 各一次；损坏声明失败后可重读，16 个不同摘要的在途读取预算有限；归档原件与压缩副本 0600，重启不改原件 mtime；联合恢复保留能力声明与压缩副本。
- 浏览器覆盖两例作答/后续等待、等待无 writer、刷新保持次序、退出重排及完成放行；第二标签只读且不轮换活动页票据；慢图片响应头 22 秒、两个准备会话 FIFO、UI 取消、组内零 API 请求、压缩协商及原有中断/未知运行/确定性补测回归。
- [1Mbps 排队原始报告](1Mbps排队本机测量.json)：20 会话先排整例队列再准备图片，最多 2 例活动；每例下载 197301 字节 PNG，原图摘要一致、同时图片流最多 1、两层队列最终清空。本次约 47.41 秒，累计响应正文 4114277 字节；下载后以 TEST_ONLY 原因终止，不执行正式试次。包含整例轮询与放行间隙，不能直接推断任意图片组的耗时。
- [双例混合采集报告](混合采集本机测量.json)：1/5/10/20 会话集中到达，最多 2 例活动；36 会话中 33 完成、3 注入终止，本次约 28.90 秒，816 次 HTTP 200、8 次明确可重试 503。真实 HTTP/SQLite/解码/重放/CSV/备份，所有预期会话结束，会话队列清空，导出/备份成功，备份 `independent:false`。
- [单例混合采集报告](单例排队本机测量.json)：同样的集中到达波次，最多 1 例活动；33 完成、3 注入终止，本次约 34.75 秒，867 次 HTTP 200、2 次明确可重试 503。队列清空，导出/备份成功且 `independent:false`。各次排队/后台竞争使请求数与耗时波动，不以单次结果宣称吞吐改善。

限速脚本只把 loopback HTTP **累计响应正文**限制为 125000 B/s，不计请求/响应头、TLS、实际 ECS 网络、主机 CPU/磁盘限制或真实浏览器渲染。混合脚本使用合成软件试次记录。两项均不能替代目标主机单例/双例正式容量或物理时序验收。

```sh
nvm use
npm run check
npm run doctor
npm run profile:mixed -- docs/混合采集本机测量.json
SESSION_CONCURRENCY=1 npm run profile:mixed -- docs/单例排队本机测量.json
npm run profile:bandwidth -- docs/1Mbps排队本机测量.json
```

## Gemini 讨论取舍与部署边界

用户要求使用 `gemini_bridge`，阿里云优化四轮及最新整例准入审查的完整输入/回复保存在 [讨论索引](gemini轻量化讨论/README.md)。采用有限下载预算、票据与实际流生命周期、预压缩代码身份核对、合并同摘要在途读取。未采用回复中的带宽/数据库路径误判、未经测量的绝对性能保证、鉴权前移或原始冲突忽略。第四轮提出的取消悬挂与未校验缓存污染未从给出的代码成立，回归保留取消清理和失败重读证据；并发重复读取作为性能改进实施。整例审查保留未关闭许可占位、过期后重排与事务提交后拒绝的既有语义，补强第二标签不轮换票据的回归。本轮没有独立重复 Gemini 的外部资料搜索。

部署步骤、独立备份、恢复与正式 gate 条件见 [部署与恢复手册](部署与恢复手册.md)。当前没有实际安装到用户 ECS；目标 Ubuntu/HTTPS/文件系统耐久性、真实手机/内置宿主、最多单例/双例活动和集中到达排队、独立业务恢复仍需对应环境验收。
