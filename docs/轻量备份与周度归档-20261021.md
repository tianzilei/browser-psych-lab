# 轻量备份：周度按需全量 + 冷归档

2026-10-21。按“20–40 条/天”的低增量负载，把每日 160 MB 全量备份改为**每周一次、无数据变化自动跳过、旧目录压缩归档**。核心 `/api/lab/jobs/backup`、maintenance worker、manifest 校验未修改。

## 当前配置

- Wrapper：`/usr/local/bin/psychlab-light-backup.mjs`（`700 psychlab`），源码在 [`scripts/backup-light.mjs`](../scripts/backup-light.mjs)
- Service drop-in：`/etc/systemd/system/browser-psych-lab-backup.service.d/wrapper.conf`
  - `ExecStart=/opt/node/bin/node /usr/local/bin/psychlab-light-backup.mjs`
- Timer drop-in：`/etc/systemd/system/browser-psych-lab-backup.timer.d/weekly.conf`
  - `OnCalendar=Sun *-*-* 03:00:00`
  - `Persistent=true`，`RandomizedDelaySec=300`
- 下一次：**2026-10-25 03:00 左右（CST，带随机延迟）**
- 备份密码文件、`BACKUP_LOCAL_ONLY=1`、local-only 行为保持不变

## 无变化跳过

Wrapper 在调用备份 API 前计算数据指纹，保存在：

`/var/lib/browser-psych-lab/research-backups/.last-backup-fingerprint.json`（`600 psychlab`）

指纹只覆盖业务数据：研究/修订、版本、会话及状态、raw/events、封存、同意、协变量、资产、图片包、诊断、标记、许可和准入队列；**排除** `lab_jobs`、`lab_audit`、`lab_meta`、`lab_pins`，避免备份自身写入触发下一次备份。

指纹在**备份开始前**计算并写入；备份期间的新写入不在本次快照中，因此下次运行会因指纹不同而再备份，避免把未捕获的数据误标为已备份。

本次验证：

- 第一次运行：无 sidecar，生成 `6485a464-3ad1-41ba-b5c1-7fcc74104842`，写入指纹
- 第二次运行：指纹相同，`needs_backup:false`，**没有生成新 bundle**，耗时不到 1 秒
- 手动 `--force`：生成 `3cb55c3d-473c-4ae2-b0a9-903765c3358a`，并把上一份 `6485a464…` 归档

> 说明：没有采用“比较 SQLite 文件 mtime”的做法。备份任务自身会写 `lab_jobs`、`lab_audit`、`lab_meta`，WAL 也会变化，mtime 判断会永远认为有变化；数据指纹避免了这个问题，也不依赖 WAL 文件状态。

## 冷归档

Wrapper 在每次备份后：

1. 保留最新 READY 原始目录；
2. 对其它 READY、无 `.keep` 的目录执行 `tar | zstd -19`；
3. 校验 `zstd -t` 和 `tar -tf`；
4. 把 `lab_jobs.state` 从 `READY` 改为 `ARCHIVED`，在 `result` 记录 archive 路径、字节数、SHA-256、原始字节数和 manifest 摘要，并写 `backup.bundle.archive` 审计；
5. 删除原始目录；
6. 只保留最近 **2 个** `.tar.zst`；更老的归档删除，对应作业改为 `PURGED` 并写 `backup.archive.prune` 审计。

实测当前 bundle：

| 对象 | 原始 | zstd-19 |
| --- | --- | --- |
| 整包 `160,569,338` 字节 | 160.6 MB | **29,303,670 字节（29.3 MB）** |
| SQLite `98,865,152` 字节 | 98.9 MB | 23.8 MB（仅数据库） |

当前本机布局：

- `df3a856e…`：删除旧版研究后的基线，已加 `.keep`，保持 READY 热目录（160 MB）
- `3cb55c3d…`：最新 READY（160 MB）
- `archives/6485a464….tar.zst`：冷归档（29.3 MB，SHA-256 `448fe9df…`）
- 4 个历史备份作业为 `PURGED`
- `research-backups` 合计约 **347 MB**

`.keep` 的目录永不压缩、不删除，因此当前是 **2 热 + 1 冷**；如果严格执行“1 热 2 冷”，删除 `df3a856e…/.keep` 后下一次运行会把它归档，最终约 **216 MB**。是否保留这个基线由研究策略决定。

## 与每日全量的对比

| 指标 | 每日全量 | 当前周度方案 |
| --- | --- | --- |
| 正常静默周 | 7 次 × 160 MB | 1 次备份或 0 次（无变化跳过） |
| 旧目录形态 | 14 个解压目录 | 1–2 个热目录 + 2 个 29 MB 归档 |
| 月度新增写入 | 约 4.8 GB | 最多约 0.64 GB（闲置周为 0） |
| 本机占用 | 约 2.2 GB | 约 0.35 GB（含 `.keep` 基线） |
| RPO | 24 小时 | 最长 7 天（无变化时实际不变） |

## 尚未启用的部分

- 没有加密：`.tar.zst` 仍是明文压缩包，目录 `700 psychlab`、文件 `600`，但不能防主机被攻破后的读取。
- 没有异地推送：`age 1.2.1`、`rclone 1.60.1` 已安装，但尚未配置公钥和远端。
- 没有告警：timer/service 失败仍只写 journal，没有 `OnFailure` 或外部心跳。
- 没有独立介质：`BACKUP_LOCAL_ONLY=1`、`BACKUP_ROOT` 为空，`collection_gate` 仍为 `CLOSED`。

## 风险提示

- 周度 RPO 意味着最长可能丢失约 7 天的新数据；如果 100–200 条/周的数据不可接受回退，可加“周中 SQLite 单文件快照”（只写 1 个约 20–30 MB 的压缩文件，不碰图片和运行器）。
- `.keep` 基线使热目录多于 1 个；如要严格控制到 1 热 2 冷，需要确认后移除 `.keep` 并让 Wrapper 归档。
- 当前 Wrapper 没有修改核心备份代码；后续若引入 age 加密/异地推送，应继续放在这个外层，保持 `/api/lab/jobs/backup` 和 manifest 逻辑不变。
