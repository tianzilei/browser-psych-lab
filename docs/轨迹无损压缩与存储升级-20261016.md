# 轨迹无损压缩与存储升级（2026-10-16）

本次将服务器的事件正文改为单份存储，并使用 gzip 无损压缩。浏览器捕获、IndexedDB 离线队列、上传协议及冻结运行器保持原合同。记录不会降采样，不改变浮点数精度，不合并或删除输入动作，不把原文解析后重新序列化。原文字节及其 SHA-256 是校验基准。

## 方案依据

- [Node.js 24 zlib 官方文档](https://nodejs.org/download/release/latest-v24.x/docs/api/zlib.html)：gzip/gunzip 与压缩级别、解压输出上限。
- [Compression Streams API](https://developer.mozilla.org/en-US/docs/Web/API/Compression_Streams_API) 和 [WHATWG 规范](https://compression.spec.whatwg.org/)：项目已有浏览器原生 gzip 上传，单纯压缩网络请求不会减少数据库中的明文正文。
- [rrweb 官方指南](https://github.com/rrweb-io/rrweb/blob/main/guide.md)：完整快照与增量事件可进一步减少重复界面，但需要维护基线依赖、断线恢复与历史版本兼容；sampling 配置还可能减少样本。本次采用能够逐字节核验的存储升级。
- [SQLite VACUUM](https://www.sqlite.org/lang_vacuum.html)：压缩正文后离线整理空闲页，实际缩小数据库文件。

## 存储合同

`lab_raw.raw` 是正文的唯一存储位置。小于 1 KiB 或压缩后节省不足 10% 的正文仍存明文；其余使用 gzip level 6，外加 12 字节头（8 字节版本标识及 4 字节原文长度）。单条原文上限保持 128 KiB。解压校验原文长度和 SHA-256，并限制输出长度。

`lab_events.envelope` 新写入固定引用 `@raw-v1`，通过完整的 `(session_id,event_id,hash)` 外键关联原文；不再重复保存正文。`lab_event_evidence` 视图统一读取旧明文和新引用。回放、封存、前驱链检查、待处理记录核对、导出、备份和恢复均使用相应解码器。预算按原始字节计数，不能通过高压缩比绕过采集上限。

实验事件、样本、封存、凭证和处置状态不因存储迁移改变。完整证据 CSV 的 `envelope` 和 `raw_utf8` 仍还原原始 UTF-8，事件导出保留会话、scope、sequence 的原有顺序；答卷 CSV 继续每会话一行并使用北京时间。独立轨迹 CSV 下载通道保持关闭。

这保证已采集证据的无损存储。回放仍是浏览器记录重建，原有节点/字节上限和浏览器事件可见范围仍适用，不能据此宣称物理屏幕录像无损。

## 离线迁移与回退

新版服务可读取历史明文，新的采集自动使用单份压缩存储。历史库压缩必须停服并先保存完整备份：

```sh
node dist/server/compact-evidence.js /私有目录/database.sqlite compact
```

命令在同一事务内核验全部原文摘要和原始 envelope 的对应关系，临时解除两个更新触发器，转换物理表示，恢复触发器，并比较迁移前后的逻辑证据摘要。迁移失败事务回滚；删除保护保持生效。迁移期间持有进程所有权标记，拒绝在活跃服务持有数据库时执行，最后 checkpoint、VACUUM 和 integrity/FK 核验。可重复执行。

库格式升为 lab schema 2。切换到旧服务前，必须用新版工具停服反向转换**当前数据库**：

```sh
node dist/server/compact-evidence.js /私有目录/database.sqlite expand
```

反向转换恢复每条原始 UTF-8 和重复 envelope，并将 lab schema 恢复为 1；迁移后新增的事件也保留。不能直接启动旧服务读取压缩库。不要用旧快照覆盖迁移后采集的数据。

升级前原始快照保留在服务器私有维护目录，不随本次压缩删除。历史备份和派生 CSV 不会自动压缩或清理，因此整个存储目录的占用不会按活跃数据库的比例下降。

## 实际数据验证

升级前数据集包含 50 个会话、10,749 条原文、39,117 个交互样本及 6,178 个界面快照。所有原文逐条压缩、解压并比较字节及 SHA-256。5 份有数据的问卷分别对比答卷导出与完整证据导出，完整 `data.csv` 的 SHA-256 相同；答案及轨迹派生 CSV 仅忽略各次导出新生成的 snapshot_id 后逐文件一致。副本反向迁移通过，接收凭证、处置状态、链位置、封存和问卷配置均保留。

| 项目 | 升级前 | 升级后 |
| --- | ---: | ---: |
| 原文与重复 envelope 正文 | 304,780,682 B | 16,120,433 B |
| 活跃 SQLite 文件（副本整理后） | 352,206,848 B | 59,891,712 B |

正文减少 94.7%，整个活跃库减少 83.0%。压缩对不同内容的收益不同：新增的纯答案本来较小，主要收益来自重复样式与界面快照。服务器单次全量基准中，gzip level 1 压缩正文约 18.3 MB、level 6 约 16.0 MB、Brotli quality 4 约 15.4 MB；选用兼容性成熟的 gzip level 6。

## 闲时压缩方案（北京时间 00:00–06:00）

2026-10-16 在同一服务器使用全部 10,749 条原文再次测量压缩成本，按上传的最多 16 条／512 KiB 划分批次：纯压缩合计 1,158 ms，单批 p50 2.00 ms、p95 3.75 ms、p99 5.11 ms、最大 6.01 ms。测量期间的进程 CPU 时间合计约 1,383 ms（含读库与统计）；这不是在线请求总延迟或峰值流量容量承诺。一次历史库迁移连同完整性校验、事务与整理约 18.2 秒。

当前保留实时 gzip，不启用每天停服或整库重写的定时任务。以下是压缩成本随负载增长后的调度设计，尚未启用：

1. 闲时窗口固定 `Asia/Shanghai` 的 `[00:00,06:00)`，不依赖操作系统默认时区。白天新事件仍校验、落盘并去除重复正文，只把较大正文登记到待压缩队列；原始接收凭证和哈希保持不变。
2. 夜间压缩使用现有专用 writer 的低优先级任务，不启动第二个数据库写者。每批最多 16 条／512 KiB，只转换物理正文，不重建业务事件、链、封存或处置状态。待压缩项与原始记录通过完整键关联，事务内更新及移出队列，可中断续跑。
3. 每批之间让出调度，目标 CPU 不超过单核 10%。前台 writer 排队、请求延迟上升或维护任务占用时暂停；先缩小批次，持续超预算再顺延。可把单批纯压缩 p99 持续超过 20 ms 或 CPU 占比持续超过 10% 作为切换调度的初始阈值，再根据实测流量调整。
4. 每批开始前重新检查时间，06:00 后不领取新批次；正在提交的小事务完成后停止。未完成项保留到下一晚。失败回滚，不删除原文，不更改接收回执，不把待压缩状态当作未接收证据。
5. 逐条解压校验原始长度及 SHA-256 后再提交，读取层继续兼容明文和 gzip。压缩后的空闲页供 SQLite 后续写入复用；整库 `VACUUM` 单独安排在该窗口内经过确认的维护时段，不让日常夜间压缩自动停服。
6. 监控待压缩字节、最老积压时间、压缩耗时分位数、writer 排队、CPU 和磁盘余量。两晚仍无法清空时报告积压；不自动降低精度、减少采样或丢弃记录。

如后续决定启用闲时模式，应将待压缩队列和限时调度作为正式服务功能实现并验证，不能把当前只允许停服使用的 `compact-evidence.js` 直接挂到在线数据库的 cron 上。

## 上线验收

正式服务已切换至 `20261016-lossless-evidence-fbab971`，历史库迁移约 18.2 秒。上线后逐条核验全部 10,749 条证据及原始哈希；50 个会话、150 个封存、19,534 条处置历史与原接收凭证均保留。5 份问卷通过真实 HTTPS 浏览器重新下载并核验文件哈希；历史操作回放可读且可逐动作推进。独立轨迹 CSV 仍返回 410；答卷 CSV 仍每会话一行，日期为北京时间。147 项单元测试、63 项浏览器测试和 15 项运行器测试通过（并行测试共用产物目录引起的一项文件冲突已隔离重跑）。

备份验证发现现有独立目标与活跃库处于同一 filesystem，备份 API 按原规则报 `BACKUP_TARGET_SAME_FILESYSTEM`。已生成的本地 bundle 共 908 个清单对象通过文件摘要、原始证据摘要、资产与冻结运行器核验，并在隔离目录成功恢复，采集门保持 CLOSED；失败作业通过正式 inventory/recover 流程解除阻塞，原文件保留。独立备份配置保持原值，未把同盘副本当作独立备份；要通过独立备份验收仍需单独挂载的备份存储。
