# 采集性能优化（2026-10-17）

本轮优化服务端 `LabStore` 的事件接收路径。相同主机顺序执行基线与优化版本，在每个范围已有 4,096 条记录时，16 条问卷事件一批的处理中位耗时由 58.750 ms 降至 6.802 ms，交互诊断由 54.209 ms 降至 8.542 ms。

## 改动

原实现每保存一条事件，都查询该会话、该范围的全部历史 `lab_raw`，计算条数与逻辑字节总量。随着记录增长，相同批次需要重复读取越来越多的原始内容。

新增 `lab_scope_usage`，按 `(session_id, scope)` 保存记录条数和逻辑 UTF-8 字节。`lab_raw` 插入触发器在同一事务内更新计数；预算检查通过主键读取这一行。所有保留的 hash 都计入预算，包括同一 event_id 的冲突记录；重复上传已存在的 hash 不增加计数，拒绝批次的原始记录与计数一起回滚。压缩后的记录按解压长度计费。

旧数据库首次启动时，在事务内按原始记录回填计数并写入版本标记，后续启动复用计数。回填失败时整体回滚。此升级需要一次历史扫描，启动时间随已有数据量增长。计数是派生数据，不改变原始事件、回执或封存结果。

冻结问卷及资源清单改为每个接收批次读取、解析一次，再传给事件验证与待处理链核对。数据只在当前请求内复用。

## 测量

环境为 macOS arm64、Node.js v24.21.0、SQLite WAL/FULL，并保留 macOS fullfsync。基线为提交 `0561ecaaaf6808e6f5b05ff74516128865352854`。两个版本依次执行同一脚本，测量时没有并行测试任务。

每个深度测量 10 批，每批 16 条新事件，并验证每批的原样重试。表中延迟是新事件批次的中位数；“历史条数”是本组测量开始时的值，测量过程中再增加 160 条。

| 事件类型 | 历史条数 | 优化前 ms | 优化后 ms | 耗时减少 |
| --- | ---: | ---: | ---: | ---: |
| 问卷修改 | 0 | 9.355 | 8.473 | 9.43% |
| 问卷修改 | 1,024 | 16.852 | 6.702 | 60.23% |
| 问卷修改 | 4,096 | 58.750 | 6.802 | 88.42% |
| 交互诊断 | 0 | 9.299 | 7.836 | 15.73% |
| 交互诊断 | 1,024 | 18.257 | 7.775 | 57.41% |
| 交互诊断 | 4,096 | 54.209 | 8.542 | 84.24% |

在 4,096 条历史记录的场景中，10 批新事件及其重试调用 `lab_raw_bytes` 的总次数由 668,080 降至 160，只计算新插入记录；冻结问卷加载由 480 次降至 20 次，即每次新上传或重试各一次。

完整数据见 [采集性能优化测量.json](采集性能优化测量.json)。这是本地同步数据库接收路径的测量，未包含 HTTP、worker RPC、真实手机或 ECS 并发容量。10 批样本的延迟会受磁盘同步与主机调度影响。

复现当前版本：

```sh
npm run profile:ingestion -- .local/ingestion-profile.json
```

脚本创建临时数据库，完成测量后清理，不使用现有研究数据。

## 验证

新增回归覆盖 UTF-8 逻辑字节、冲突 hash 与重试、跨范围与跨会话隔离、旧库回填及失败回滚、压缩/展开和重启。现有预算测试增加拒绝批次后计数不变的断言；固定操作次数测试检查上传开销不再依赖历史字节扫描。

类型检查、生产构建、数据库冒烟检查通过；180 项单元测试、68 项端到端浏览器测试、16 项运行器浏览器测试与 4 项第二轮逻辑集成测试全部通过。
