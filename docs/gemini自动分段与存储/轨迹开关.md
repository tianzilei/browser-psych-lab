## Gemini 原文

本次针对 `record_interactions: boolean` 独立开关方案的设计审阅，结论是**架构设计理念正确且对不可变历史数据的保护得当**（采用可选字段、省略不补默认值以保护旧哈希、在入口顶层提前短路阻断监听与定时器）。

为确保生产落地时不破坏已有数据链完整性，指出以下 **4 个真实缺口**并给出最小改动建议，均在现有代码结构内闭环，不引入新基础设施：

### 1. 真实缺口：`false` 伪对象未阻断 `Ledger` 对空 Scope 的生成与链式封存

**问题现象**： 方案提到当 `enabled: false` 时，“返回空的 `screen / flush / stop`，不采集，不创建 d-ui 事件或上传”。 但在原系统契约中，页面初始化或问卷提交流程中通常存在以下隐式调用：

1. 页面加载初始化时，系统是否预先向 `Ledger` 注册/声明了空的 `d-ui-xxx` scope？
2. 页面提交或页面跳转（Page Seal）时，上层调用者是否无条件调用了 `interaction.flush()` 或 `Ledger.seal(scope)`？
3. 如果 `flush()` 返回 `Promise.resolve()`，但 `Ledger` 内部如果仍持有对该 scope 的引用或元数据记录（如生成了空 scope 记录但事件数为 0），在 `sync` 时会不会将一个“空事件列表的 outbox 任务”推送至服务端？

**修正建议**：

- 确保 `enabled: false` 时，**彻底不调用任何 `Ledger.interaction` 的创建或注册逻辑**。
- 返回的空交互控制器（Stub/No-op Object）契约必须严格闭环：`const NOOP_INTERACTION_CONTROLLER = {
  screen: () => {},
  flush: () => Promise.resolve(),
  stop: () => {},
  // 如果原控制器暴露了 scopeId 或 ledgerRef，此处必须为 null 或 undefined，
  // 确保任何上层 seal 逻辑跳过该 scope，绝不写入 IDB outbox
};`

### 2. 真实缺口： study-v1 与嵌套 questionnaire-v1 的开关继承/冲突语义未明确

**问题现象**： 方案同时在 `study-v1` 和 `questionnaire-v1` 顶层增加了可选字段 `record_interactions: boolean`。 在心理学实验平台的典型组合中，一个 `study-v1` 协议往往会引用或内嵌一个或多个 `questionnaire-v1` 问卷，或者由 Study Runner 调度运行问卷：

- 如果 `study-v1` 显式设为 `record_interactions: false`，但其内嵌引用的问卷 JSON 中**省略该字段**（按规则应 fallback 为采集）或设为 `true`，以哪个为准？
- 反之，如果 Study 设为 `true`，但某个长问卷显式设为 `false`，是否允许长问卷局部关闭？

**修正建议**： 必须定义严格且无歧义的“就近优先”或“单向禁用”决议函数（推荐**就近（子级优先）+ 父级默认值继承**）：

```
function resolveRecordInteractions(
  studyConfig?: { record_interactions?: boolean },
  questionnaireConfig?: { record_interactions?: boolean }
): boolean {
  // 1. 问卷本身有显式配置（true/false），直接以问卷自身声明为准
  if (typeof questionnaireConfig?.record_interactions === 'boolean') {
    return questionnaireConfig.record_interactions;
  }
  // 2. 问卷省略，但 Study 顶层有显式配置，继承 Study 的意图
  if (typeof studyConfig?.record_interactions === 'boolean') {
    return studyConfig.record_interactions;
  }
  // 3. 两者均省略，遵循历史行为默认采集
  return true;
}
```

*注：该决议仅在运行时计算，严禁将计算结果写回或补入解析后的协议 AST，避免破坏 AST 序列化与 Hash 校验。*

### 3. 真实缺口：页面刷新（Page Reload）恢复会话时的配置丢失风险

**问题现象**： 用户在做长问卷时可能意外刷新页面或中途离线重进。 当前平台通过 IDB 恢复草稿与未完成的会话状态。方案中提到“显式 false 由参与问卷、固定刺激 runner、自定步长图片评分 runner 三个入口传入”。 如果受试者在问卷中途刷新：

- Runner 恢复该受试者会话时，`enabled` 标记是**重新从当前会话绑定的冻结协议 JSON 中读取**，还是从浏览器临时内存/URL 参数中读取？
- 若从草稿恢复，且草稿状态对象遗漏了该布尔标记，是否会导致页面刷新后意外回退为 `true`，从而使后半段问卷重新生成 `d-ui` 记录并上传？

**修正建议**：

- 恢复入口必须与首次初始化执行**同一条**协议解析路径，确保 `enabled` 状态始终且唯一派生自持久化的冻结协议定义，禁止在 session state 中独立缓存可能与协议失步的副本。

### 4. 真实缺口：测试验证应补足“旧 pending 上传在开关为 false 页面中的行为”

**问题现象**： 方案提及“仅新版本新会话生效，不清理旧记录、不拦截旧 pending 上传”。 在实际客户端执行时，后台的 `sync` 机制通常是全局单例或伴随 Runner 运行的。如果受试者之前存在由旧问卷遗留的 `d-ui` pending 记录（尚未上传完），接着进入了一个设为 `false` 的新问卷版本：

- 全局 Sync 进程是否会在当前新问卷作答期间继续在后台消耗带宽上传旧 `d-ui` 记录？（这是预期且正确的，保证旧数据不丢）。
- 但必须警惕：当受试者完成该新问卷并点击提交时，新问卷的提交栅栏（submit barrier）是否在等待“所有 Outbox 清空”？如果旧的 pending 记录由于此前 413 超限或弱网一直挂在 Outbox 里，是否会导致一个**本已关闭轨迹采集的问卷依然被旧轨迹阻断提交**？

**修正建议**：

- 在端到端验证用例中追加一项：**“构造本地 Outbox 存有未决历史 d-ui 任务，进入 record_interactions: false 问卷，验证新问卷答案提交时其 barrier 的关联范围”**。确保新问卷的答案提交只阻塞其本会话关联的任务，或若阻塞全局 Outbox 时，旧任务遇到 413 仍能按前次确定的 512MiB 规则顺利落库，避免因旧债卡死新问卷。

### 总结

除上述 4 点（**确保 Stub 不注册空 Scope**、**统一父子 Schema 继承语义**、**刷新恢复源唯一性**、**核验跨会话 Outbox 提交屏障**）外，整体方案对模式兼容、哈希链与设备协变量/评分修订保留的设计均十分严谨，补齐上述边界后即可直接实施。
