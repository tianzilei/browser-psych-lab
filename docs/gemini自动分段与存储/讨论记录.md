### A. 自动分段与兼容方案评估及必须修正的 3 项边界

**评估结论**：接受当前方案。在不改变受试者答题流程、不重写旧哈希链前提下，将分段下沉至客户端 Ledger 自动触发，并对服务端旧 `d-ui-` 仅做单项放宽，是阻断 413 级联阻塞答案提交的最优最小改动。

但在落地实施前，必须修正以下 3 项边界：

1. **分段判定必须基于“序列化前精确字节计算”，而非粗粒度预估**
  - **必要性**：UTF-8 字符（如中文文本输入）与 JSON 特殊字符转义（Unicode 编码、斜杠、引号）会导致预估大小与实际生成的 HTTP 请求体存在非线性差异。若仅靠预估 + 4096 字节余量，极端情况下可能正好在边界溢出（比如单批接近 128KiB 限制时）。
  - **实施规则**：在 `append` 屏障内部，必须针对本批即将序列化的 Payload 直接计算 `Buffer.byteLength(JSON.stringify(envelope))`，当 `current_bytes + payload_bytes > 8MiB` 或 `current_batches >= 256` 时立即封段。
2. **跨段时钟戳单调性与命名隔离（Clock-Segment Collision）**
  - **必要性**：当前段命名规则为 `d-ui-${clock}-${segment}`。若短时间内（如快速滚屏或高频连续输入）触发分段，且 `clock` 取自毫秒级系统时钟，可能出现同毫秒下 `clock` 相同；若前端发生网络错误重试、重置或并发保存，可能导致 scope 键名冲突或服务端唯一索引碰撞。
  - **实施规则**：该 session 实例内必须维护全局严格单调自增的 `segment_index`（0, 1, 2...），段命名固定格式为 `d-ui-${session_start_clock}-seg${segment_index}`，且每段创建时重置 `sequence = 0`、`previous = null`，严格避免重试造成的键冲突。
3. **Outbox 队列排空顺序与事务阻断解耦（诊断失败不得级联丢弃答案）**
  - **必要性**：当前逻辑为“sync 上传全部 outbox 后才提交答案”。虽然分段将单段控制在 8MiB / 256 批，但弱网或断网恢复后，多个 `d-ui` 分段与答案可能同时在 outbox 中排队。若任一历史分段因偶发网络波动或服务端旧校验失败，不能导致答案提交一直被挂起直到受试者关页。
  - **实施规则**：Outbox 必须维持因果序上传（严格按产生时间），但一旦诊断分段返回不可重试的 4xx（如格式异常或校验异常），必须记录本地软错误并允许后续答案 scope 尝试提交，严防诊断链路单点失败永久阻塞答案闭环。

### B. 磁盘百分比计算口径与界面标签语义

在 Linux/Unix 环境下，文件系统通常为 `root` 用户预留约 5% 的保留空间（即 `bfree - bavail`）。对于普通非 root 进程（如 Node.js 运行用户），实际**可写入的上限**是 `blocks - (bfree - bavail)`。

#### 1. 口径选择

选择 **`(blocks - bavail) / (blocks - (bfree - bavail))`**（或工程上通用的 `(blocks - bfree) / blocks` 对应物理盘；针对非 root 用户可用性，推荐遵循 `df -h` 标准口径）。

*为了与系统运维工具（如 `df -h`）完全一致，避免管理员误判，推荐采用标准非 root 口径：*

$$
\text{已用百分比} = \frac{\text{blocks} - \text{bfree}}{\text{blocks} - \text{bfree} + \text{bavail}} \times 100\%
$$

*若追求最小实现与无歧义，可直接使用标准物理占用口径：*

$$
\text{物理已用百分比} = \frac{\text{blocks} - \text{bfree}}{\text{blocks}} \times 100\%
$$

#### 2. 界面标签与口径呈现建议

建议采用清晰分立的标签，直观展示用户最关心的“剩余可用空间”：

| 字段 | 对应底层计算 | 界面呈现示例 |
| --- | --- | --- |
| **存储使用率** | `(blocks - bfree) / blocks * 100%` | **78.4%** |
| **已用 / 总量** | `(blocks - bfree) * bsize` / `blocks * bsize` | 39.2 GiB / 50.0 GiB |
| **当前用户可用** | `bavail * bsize` | **可用: 8.3 GiB**（受预留空间限制） |

> **提示说明**：在卡片下方以小字标注：“*统计范围：数据盘整盘文件系统（非单一数据库文件）*”。

### C. 接口方案与管理页无侵入刷新设计

#### 1. 接口选择：扩展复用 `GET /api/lab/operations`

**推荐扩展已有接口**，原因如下：

- **避免冗余路由**：`operations` 本身已执行鉴权和 `statfs(STORAGE_ROOT)`，只是原来仅返回了 `free_bytes = bavail * bsize`。
- **改动最小**：只需在原有接口返回的 JSON 对象中，补充 `storage: { total_bytes, used_bytes, avail_bytes, used_percent }` 字段，服务端改动仅 3~4 行代码，无需新建控制器、测试路由和鉴权中间件。
- **开销可忽略**：`statfs` 是常数时间 $O(1)$ 的内核系统调用，不涉及磁盘 IO 遍历，与独立接口相比，合并返回几乎没有多余系统负载。

#### 2. 管理页刷新设计（隔离 DOM，不触碰列表）

为了彻底避免 60 秒轮询破坏用户正在编辑的改名输入框或文件上传表单：

1. **DOM 结构解耦**： 在管理员页面布局顶部保留独立的 `<div id="storage-status-card"></div>` 容器，**严禁**让 `list()` 或全局 render 函数重写该容器的父级 innerHTML。
2. **轻量独立轮询控制器**：`let storageTimer = null;

  try {
    const res = await fetch('/api/lab/operations');
    if (!res.ok) throw new Error('HTTP ' + res.status);
    const data = await res.json();
    updateStorageCardDOM(data.storage, new Date());

2. **历史积压超限补传与答案闭环用例（旧数据兼容性）**

请求 `bpl-scope-storage-20261011-2`；结果 `res_d52d30c510651127fc6b`。

该方案已收敛完备，逻辑自洽且边界清晰，可以实施。

若要达到生产上完全闭环，只需注意以下 **2 个具体实现细节**：

1. **分段临界点的单批事件溢出防护（避免死循环）**
  - **问题点**：当即将写入的批次本身体积就非常大时（例如包含长文本粘贴或高分辨率快照，单批体积接近甚至超过 8MiB 阈值），若当前段已有数据，系统会触发新建分段；但在新段中，若该单批事件的精确字节数依然大于 8MiB，若逻辑写为“只要大于 8MiB 就继续封段新建”，会导致空段死循环。
  - **处理方式**：分段条件需增加“当前段非空”判定，即 `(current_batches > 0 && (current_bytes + payload_bytes > 8MiB || current_batches >= 256))` 才切新段。新段的首批（`current_batches === 0`）无论多大都必须允许写入（只要单事件未超 128KiB、单批未超上限），写入后立即成为饱和段。
2. **存储轮询在浏览器标签页后台恢复时的防抖与重叠保护（Visibility Change Race）**
  - **问题点**：当标签页长时间处于后台后重新切回前台（触发 `visibilitychange` 事件），如果业务代码同时监听了该事件来立即刷新，而 `setInterval` 此时正好也处于触发窗口，或者前一次在途请求（如弱网慢响应）尚未返回，可能引发竞态。
  - **处理方式**：确保“只允许一次在途请求”使用严格的布尔锁（如 `isFetching` 标志）或 `AbortController`；若切回前台时距离上次成功刷新已不足 60 秒（例如仅在后台停留了数秒），无需立即触发，直接复用既有计时器节拍即可。
