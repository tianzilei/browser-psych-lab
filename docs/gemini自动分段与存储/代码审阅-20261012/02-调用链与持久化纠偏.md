### 一、 核心推导主动复核与定级核实

#### A. 关于“upload 无限空转 / 定时器重试风暴”

- **代码事实核实**：
  1. `upload()` 入口有 `running` 互斥锁，执行期间不允许第二个 `upload()` 并发进入。
  2. 进入 `do { requested = false; ... } while (requested && !disposed)` 循环后，`requested` 在每轮迭代顶部被重置为 `false`。
  3. 只有受试者发生交互（答题）调用 `schedule()` 时，`clearTimeout(timer)` 才会刷新 700ms 防抖定时器；当 700ms 到期触发 `trigger()` 时，才会将 `requested = true`。
  4. 如果受试者**停止作答**，700ms 后触发的最后一次 `upload()` 走完 `sync()` 并且在 `!m.pending[page.id]` 跳出 inner 循环后，底部的 `requested` 必定为 `false`。`do...while` 必然正常终止，绝不会发生“无输入时的死循环空转”。
  5. 只有在**受试者高频连续答题**期间，当某次 `upload()` 正在网络 I/O 时受试者再次产生输入，才会在当前循环结束后多跑一轮迭代。
- **裁定**：**撤回“死循环”定性，降级为性能开销与网络冗余优化（P2/优化项）**。

#### B. 关于“段间转换时状态文案失真（永远看不到已同步）”

- **代码事实核实**：
  1. 30 题段填完后，UI 触发快照，写入 `pending[page.id]` 并推进 `editIndex` 到下一段。
  2. `upload()` 的 inner `for(;;)` 循环逻辑：`await api.sync(page.id);
m = await api.ledger.state();
if (!m.pending[page.id]) break;
await api.seal(page.id); // seal 内部 await this.refresh()，服务端推进 page_index`在执行 `api.seal(page.id)` 成功后，`api.refresh()` 使得 `api.session.page_index` 推进到下一段。
  3. `for(;;)` 循环**没有跳出**，而是继续执行下一轮迭代： `const page = protocol.pages[api.session.page_index];` 取到了**新的一段**！ 紧接着立即执行 `await api.sync(page.id);`。
  4. 此时若受试者在新的一段已经产生了哪怕 1 条 revision，该 revision 在这次 `sync(page.id)` 中会被直接上传并 ACK。
  5. 当新的一段尚未完成时，新段的 `m.pending[new_page.id]` 为空，循环在 `if(!m.pending[page.id]) break;` 正常退出。
  6. 退出后检查：`const pending = await api.ledger.batch();`。若此时受试者停手，新段的 revisions 已经在第 3 步被 ACK 并从 outbox 删除，`pending.length` 为 0，**文案会正确变为“当前答案已同步至服务器”**。
- **裁定**：首轮关于“界面将长期停留在等待上传、永远看不到已同步”的推导不成立，**予以撤回**。

#### C. 关于“无参 sync 必然导致未来 scope 越界 quarantine”与“二次完成”

- **代码事实核实**：
  1. 查看 `ledger.ts` 的 `batch(scope?: string)` 过滤实现：`// Never upload a future questionnaire scope before its predecessor seals.
if (scope !== undefined && row.scope !== scope && !row.scope.startsWith('d-ui-')) {
  cursor = await cursor.continue();
  continue;
}`如果 `scope === undefined`，过滤短路失效，游标确实会提取 outbox 中所有待传事件。
  2. **但是分析数据生产路径**： 问卷答题时，`adaptive-survey.ts` 内部严格绑定当前 `editIndex`：只有当前段填完并生成 snapshot，才会将 `editIndex` 递增到下一段。在单实例正常流转下，IDB 的 outbox 中**天然不存在跨多段的未封存 revision**。
  3. 关于 `ParticipantAPI.complete()` 的调用时机：`// adaptive-survey.ts:
if (finishing && api.session.page_index === protocol.pages.length) {
  await options.complete(); break;
}`此时 `page_index === protocol.pages.length`，即**所有 7 个段均已在服务端完成 seal**。此时 outbox 中根本不可能再有问卷的未来段，因为全量段都已经结清！
  4. 关于“二次完成”：`options.complete` 触发后，`participant.ts` 中执行 `await api.complete(); await restore();`。`restore()` 顶部首先 `recorder?.stop(); disposePage?.();`，旧的 `mountAdaptiveSurvey` 实例被立即注销，`disposed = true`。后续 `restore` 检查 `s.state === 'COMPLETED'`，直接挂载 `mountEnding`。
- **裁定**：首轮关于“无参 sync 必然越界”属于未结合上层状态约束的过度外推；在既有正常控制流下不可能越界。**从 P1 降级并转为依赖防御性编码建议**。

#### D. 关于“dispose 缺乏在途 AbortController 的真实数据影响”

- **代码事实核实**：
  1. 页面持有浏览器 `navigator.locks` 全局会话互斥锁（`lab-version-${version}`），多标签页并发已被物理拦截。
  2. `restore()` 通过全局 `busy` 标志排队（`action(restore)`），同一时间只有一个 `restore` 流程在跑。
  3. `Ledger` 的所有状态更新均通过 `this.serialized()` 串行 Promise 链与 IndexedDB `strict` 事务排队。
  4. 如果组件销毁（例如网络错误降级进入 `recovery()`）时有未决的 `api.refresh()` 或 `api.sync()`，这些请求即使在后台晚些返回，写回的也是原始事件的 receipt ACK，或者只是一次只读 `refresh`。由于 `writer_epoch` 和 `strict` 事务保护，**绝不可能造成本地哈希链分叉或数据破坏**。
- **裁定**：缺失 abort 仅存在少许网络资源浪费，不存在真实数据链损坏风险，**由 P2 降级为非阻塞代码优化**。

### 三、 经上下文复核后，代码中真正存在且必须注意的剩余问题

排除原先基于局部片段的推论后，在全链条交互中，以下 **3 个边缘边界** 具有实际工程意义：

#### 1. [P1] 网络恢复时 `admission` 失效与 `upload` 的静默跳过漏洞

- **触发路径**： 受试者离线填完一个 30 题段并等待。由于断网超过租期（`deadline` 过期或心跳失败），`api.admission.check()` 抛出 `ADMISSION_EXPIRED`。 当网络恢复时，`window.online` 触发 `trigger()` -> `upload()`：`// adaptive-survey.ts
let admitted=false;try{api.admission?.check();admitted=!!api.admission;}catch{}
if(!admitted)await options.reconnect();`如果此时网络虽通，但服务器负载高或受试者排队状态变更，`options.reconnect()` 抛出异常（例如 `SESSION_WAITING` 或瞬时 503）。 异常被 `upload()` 的 `catch` 捕获：`if(retryable(error))note(..., true);`此时 `retry.hidden = false`。**关键问题**：若受试者在离线状态下已经点到了问卷末尾（`finishing === true`），UI 此时停留在 `作答已结束，正在确认保存...`。如果受试者没注意上方小字去点“重试保存”，系统设置的自动重试定时器是 15 秒（`setTimeout(trigger, 15000)`）。在这 15 秒内，没有任何动画或进度提示，由于答卷已经结束，没有新的输入事件可以触发 `schedule()`，受试者极易误认为浏览器死锁而直接关闭标签页，导致尚未完成的 seal 和 finalize 丢失。
- **最小修改**： 在 `finishing === true` 状态下，若进入重试区间，重试定时器应从 15 秒缩短至 3~5 秒，并在文案中明确提示“*正在自动重新连接并封存，请勿关闭…（5秒后重试）*”。

#### 2. [P1] `upload()` 中 `api.session.seals` 补全时的异常穿透边界

- **代码事实**：`// A lost seal response may leave the server ahead of the local receipt.
for(const seal of api.session.seals){
  const scope=seal.manifest.scope;
  if(m.pending[scope]&&!m.pending[scope]!.seal)await api.ledger.seal(scope,seal);
}`查看 `ledger.ts` 的 `seal()` 方法：`if(!p||seal.status!=='SEALED'||seal.algorithm!=='exact-set-and-chain-v1'||
   manifestText(seal.manifest)!==manifestText(p.manifest)||
   seal.manifest_hash!==await sha256(manifestText(p.manifest)))
  throw new Error('SEAL_MISMATCH');`这是非常健壮的密码学精确匹配。但存在一个极限场景： 若客户端因为本地存储空间不足（QuotaExceededError）导致此前某个快照写入时 IDB 发生截断，或者本地 manifest 构造与服务端记录产生微小偏差： `api.ledger.seal` 将抛出 `SEAL_MISMATCH`。 由于 `SEAL_MISMATCH` 不是 `isConnectionFailure` 也不是 `ADMISSION_EXPIRED`，它会穿透 `retryable(error)`，直接调用 `options.error(error)` 触发顶层的全局 `recovery(error)`。
- **后果**： 受试者会被直接踢出作答界面，进入全屏报错恢复卡片。虽然保证了“不伪造保存成功”的铁律，但缺乏重试挽救机会。
- **建议**：保持当前实现。对于哈希或 Manifest 不匹配的严重协议分歧，直接停机报错是符合不可变数据审计要求的正确做法。

#### 3. [P2] 页面卸载（pagehide）信标中的 keepalive 请求与未决 Scope 竞争

- **代码片段**：`window.addEventListener('pagehide',()=>{
  recorder?.stop();
  admissionController?.abort(new Error('页面已关闭。'));
  if(owned&&api?.session.state==='ACTIVE'&&api.session.permit?.state!=='ISSUED')
    void fetch(api.path('release'),{method:'POST',...,keepalive:true});
});`在受试者完成全部答题并点击完成的瞬间，若受试者在 `finalize` 网络包发出但未回包时关闭了页面： `pagehide` 会发出 `release` 请求。由于服务端当前 `session.state` 仍为 `ACTIVE`，服务端会提前释放该会话，而此时服务端的最后一个 seal 可能已被确认，但 finalize 未标记。 受试者下次重新打开链接时，`restore()` 中检查 `s.state` 会依然是 `ACTIVE`，但 `m.pending` 均已 seal，系统能顺利自动触发兜底 `complete()` 闭环。因此该逻辑具有自愈性，无须额外改动。

### 审阅结论

在全面接入 `Ledger` 严格事务、`Web Locks` 单例互斥及完整调用链后可以明确：**原代码的并发控制与一致性设计远比单看视图层模块时严密**。

1. 第一轮提出的 **“死循环”与“状态永久显示未同步”推导不成立，已正式撤回**。
2. 架构上无需对数据流和事务核心做破坏性重构，底层对哈希链、严格序列化与 Exact Manifest 的校验完全合规。
3. 唯一的体验级安全隐患在于 **末尾等待状态下重试间隔过长（15s）可能导致受试者误以为死机而关页**，建议在结束等待态微调重试节拍。
