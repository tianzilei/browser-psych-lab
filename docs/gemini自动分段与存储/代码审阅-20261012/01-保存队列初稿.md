### P0：阻塞保存流程或导致数据卡死/状态不一致的缺陷

#### 1. `upload()` 死循环：网络恢复后在未 Snapshot 的当前 Page 上无限空转

- **触发顺序**：
  1. 受试者正在作答当前段（例如 `page_0`），触发了若干 `PAGE_REVISION`。
  2. 此时 `m.pending[page.id]` 为 `undefined`（因为当前段只有 revision，只有在 30 题填完点击下一页触发 snapshot 时才会写入 `pending`）。
  3. `upload()` 被 700ms 定时器触发。
  4. 进入循环：`for(;;){
  if(disposed)break;
  const page=protocol.pages[api.session.page_index];if(!page)break;
  await api.sync(page.id); // ① 同步了当前段的 revisions
  m=await api.ledger.state();
  if(!m.pending[page.id])break; // ② 此处 break 跳出循环！
  await api.seal(page.id);
}`
  5. 跳出 inner 循环后，执行：`const pending=await api.ledger.batch();
note(pending.length?'答案已保存在本机，等待按顺序上传。':'当前答案已同步至服务器。');`
  6. 在 `finally` 之前，`while(requested && !disposed)` 发生判定：受试者在刚才持续点击选项，或者 `schedule()` 使得 `requested === true`。
  7. 循环回到顶部重新执行 `do { ... } while(requested)`，不断向服务端发送空 batch 的 `sync(page.id)` 和 `refresh()`，产生非必要的网络轮询风暴。
- **后果**：由于只要有单题输入就会触发 `schedule()`，且若受试者在段内答题节奏快，`upload()` 会在 inner 循环 break 后立即因 `requested=true` 再次执行，频繁调用 `api.refresh()` 和 `api.sync()`，浪费弱网下的宝贵连接与电量。
- **最小修改**： 在 `do { ... }` 循环内部，如果发现当前未达到 seal 条件（`!m.pending[page.id]`）且当前 scope 的 revisions 已经通过 `sync(page.id)` 完全 ack（即 `(await api.ledger.batch(page.id)).length === 0`），即使外层 `requested === true`，若只是 revision 更新且没有新未上传事件，应退出本次 `upload()`，等待下一次定时器防抖或下一个 snapshot 触发。
- **回归用例**：
  - *用例*：在单段内（如第 5 题到第 15 题）连续快速点击选项，监控 HTTP 网络面板。
  - *预期*：网络请求应当被防抖合并，不能在无新事件时持续发起 `sync` + `refresh`。

#### 2. `upload()` 失败时递归/定时器重试逻辑导致的 Timer 泄漏与竞态风暴

- **触发顺序**： 在 `finally` 块中：`finally{
  running=false;
  if(requested&&!disposed){requested=false;schedule();}
  else if(retry.hidden===false&&!disposed)timer=setTimeout(trigger,15000);
}`
  1. 假设网络断开，`upload()` 抛出连接异常，进入 `catch`，执行 `note(..., true)`，此时 `retry.hidden = false`。
  2. 执行 `finally`：由于网络断开期间没有新输入，`requested` 为 `false`，进入 `else if`，设置了一个 15 秒的 `timer = setTimeout(trigger, 15000)`。
  3. 此时受试者点击了选项，触发答题回调中的 `schedule()`：`function schedule(){clearTimeout(timer);timer=setTimeout(trigger,700);}`清除了 15 秒定时器，重置为 700ms 定时器。
  4. 700ms 后触发 `trigger()`，`upload()` 再次执行并再次失败，`retry.hidden` 依然是 `false`，再次排队 15000ms。
  5. **致命竞争**：若用户手动点击了“重试保存”按钮，`trigger()` 被调用，但若此时 `upload()` 正在运行（例如慢请求超时未返回，`running === true`），`upload()` 开头 `if(running||disposed)return;` 直接返回！但此时 `requested` 被赋值为 `true`。原在途请求失败退出后，在 `finally` 里又执行了 `schedule()`。此时如果重试按钮被连续点击，没有任何防抖保护。
- **后果**：弱网连接超时或挂起期间，手动点击“重试”无法打断超时的底层 fetch，且可能导致多个重试计划叠加。
- **最小修改**：
  1. `retry` 按钮点击时，若 `running === true`，应给按钮增加 disabled 态或提示“正在尝试同步中...”，避免无意义重入。
  2. 在 `trigger()` 入口不仅 `clearTimeout(timer)`，还要显式将 `timer = undefined`，并在 `dispose` 中彻底置空。
- **回归用例**：
  - *用例*：断网状态下快速连续点击 5 次“重试保存”按钮，再恢复网络。
  - *预期*：只应有 1 个在途重试请求，网络面板不应并发多条重复的 `refresh/ingest` 请求。

### P1：合同边界不严密、状态显示失真或可能触发服务端 Quarantine

#### 1. 状态文案“已保存在本机 / 已同步至服务器”在段间边界处失真

- **触发顺序**： 当一个 30 题段做完，触发 `PAGE_SNAPSHOT`：`// 回调中：
await api.ledger.append(page.id,'PAGE_SNAPSHOT',{answers:data},[...path,page.id],data);
path.push(page.id);
editIndex++;await show();trigger();`在 `upload()` 内部：`const pending=await api.ledger.batch();
note(pending.length?'答案已保存在本机，等待按顺序上传。':'当前答案已同步至服务器。');`
- **问题与后果**： `pending = await api.ledger.batch()` **不传参数**。按照底层定义，`batch()` 不带参数默认会返回 IDB 中**所有**未 ack 的事件（包括下一段已经产生的 revision，或者包含未来段）。 更关键的是：此时本段如果刚在服务器端完成 `seal`，但由于 `show()` 已经推进 `editIndex` 并允许用户在新段输入，新段的 revisions 已经写入了 IDB。 因为新段不能提前上传（否则服务器 quarantine），这些新段的 revisions 必然留在本地。此时 `pending.length` 恒大于 0。 **结果是**：界面将长期停留在“答案已保存在本机，等待按顺序上传”，哪怕当前能够上传的数据已经全部 100% 同步并被服务端 ACK，受试者也永远看不到“当前答案已同步至服务器”，造成严重的“系统卡住没上传”的心理焦虑。
- **最小修改**： 状态提示应当区分“可上传范围”**与**“当前服务器同步进度”：`// 检查当前或已封存段是否还有未 ACK 的事件
const currentScopeEvents = await api.ledger.batch(page ? page.id : undefined);
note(currentScopeEvents.length ? '答案已保存在本机，正在排队同步…' : '当前已答部分已安全同步。');`
- **回归用例**：
  - *用例*：在完成第 30 题进入第 31 题后，停止输入等待 2 秒。
  - *预期*：当第 30 题所属段 seal 完成且第 31 题尚无未决上传时，界面应给出明确的成功同步反馈，而不是提示有等待上传的数据。

#### 2. `api.session.seals` 恢复与重试时的未来 Scope 潜在越界漏洞

- **代码段**：`for(const seal of api.session.seals){
  const scope=seal.manifest.scope;
  if(m.pending[scope]&&!m.pending[scope]!.seal)await api.ledger.seal(scope,seal);
}
for(;;){
  if(disposed)break;
  const page=protocol.pages[api.session.page_index];if(!page)break;
  await api.sync(page.id);
  m=await api.ledger.state();
  if(!m.pending[page.id])break;
  await api.seal(page.id);
}`
- **依赖未给合同的风险**： 如果服务器由于断网恢复，返回的 `api.session.page_index` 推进了，但是 `api.session.seals` 中包含历史已确认的 seal。 在内部循环中： `await api.sync(page.id);` 调用的是 `ParticipantAPI.sync(page.id)`。而在 `ParticipantAPI.sync` 的精确片段中：`async sync(scope?:string){
  await this.ledger.drain();
  await this.syncEnvironment();
  for(;;){
    const events=await this.ledger.batch(scope); // ①
    if(!events.length)break;
    const result=await request<{receipts:Receipt[]}>(this.path('ingest'),...);`在第 ① 行：**如果调用方没有传入 `scope`，即 `scope === undefined` 时，`batch()` 会取出全量事件！** 而在 `ParticipantAPI.complete()` 中：`async complete(){
  await this.sync(); // 【严重风险点】：此处没有传 scope！
  await this.refresh();`
- **后果**： 在问卷最后调用 `complete()` 时，执行了无参数的 `await this.sync()`。如果在此刻或离线异常恢复路径下，本地 IDB 中由于某些边界情况残存有非法 scope 或未对齐 scope 的事件，无参 `sync()` 会一口气将所有 events 打包推给 `/ingest`，直接触发服务器端 **SCOPE_QUARANTINE**。
- **最小修改**： `ParticipantAPI.complete()` 中禁止调用无参 `this.sync()`。或者在 `ParticipantAPI.sync` 内部强制做守卫：`// 必须严格校验当前 scope 是否与 server page_index 对齐，杜绝无参泄露未来 scope
const targetScope = scope ?? protocol.pages[this.session.page_index]?.id;
if (!targetScope && this.session.page_index < protocol.pages.length) {
  throw new Error('INVALID_SYNC_SCOPE');
}`
- **回归用例**：
  - *用例*：模拟最后一题提交时，离线写入一个虚拟未对齐 scope 事件，调用 `options.complete()`。
  - *预期*：不应向服务端发送包含未来/越界 scope 的 ingest 请求。

### P2：鲁棒性与生命周期边缘细节

#### 1. `mountAdaptiveSurvey` 卸载时的在途异步请求未截断（AbortController 缺失）

- **现象**： 当组件注销（返回的 dispose 函数被调用）时：`return()=>{
  disposed=true;disposePage();clearTimeout(timer);
  window.removeEventListener('online',trigger);
  window.removeEventListener('offline',offline);
};`虽然将 `disposed = true`，但是如果此时正好有 `await api.refresh()`、`await api.sync()` 或 `await api.seal()` 挂在网络 I/O 上，这些 Promise 依然会继续执行直到网络返回。
- **后果**： 虽然代码各处有 `if(disposed) return;` 保护，但网络返回后依然会执行 `this.ledger.acknowledge(...)` 和 `this.ledger.seal(...)`。这对于底层 IDB 事务本身并无坏处，但如果外部路由已经切走并重开了一个新的会话实例，会发生**两个实例并发竞争同一个 IndexedDB ledger**，导致版本冲突或序列号不匹配。
- **最小修改**： 在 `mountAdaptiveSurvey` 作用域内维护一个 `abortController = new AbortController()`，在 dispose 时调用 `abortController.abort()`，并将其 `signal` 透传给底层 API 请求。

#### 2. `finishing` 标志与 `options.complete()` 的二次触发竞争

- **现象**： 在 `show()` 判定到达末尾时：`if(!page){
  finishing=true;
  mount.replaceChildren(...);
  trigger();
  return;
}`如果受试者在弱网下多次触发 `trigger()`（例如网络抖动触发了 `window.online`），在 `upload()` 内部：`if(finishing&&api.session.page_index===protocol.pages.length){
  await options.complete();break;
}`如果 `options.complete()` 执行较慢（包含 finalize 网络往返），此时又进来了另一个并行的 `trigger()` 或 `upload()`，虽然有 `running` 锁，但在 `upload()` 执行完毕释放 `running` 后，若页面尚未完成跳转，下一次 `trigger()` 会再次调用 `options.complete()`。
- **最小修改**： 增加 `let finalized = false;` 锁：`if(finishing && !finalized && api.session.page_index === protocol.pages.length){
  finalized = true;
  await options.complete();
  break;
}`

### 审阅结论总结

当前模块的主体架构（串行 drain、按 page.id 单段同步、利用 session.seals 弥补 lost seal response、严格状态机推进）**设计思路非常扎实**。

当前可证明且必须修复的重点是：

1. **解决单段内未产生 snapshot 时 `upload()` 的反复空转请求**（P0）；
2. **切除 `complete()` 中无参 `sync()` 广播导致的未来 Scope 泄漏与 Quarantine 隐患**（P1）；
3. **修正多段间状态栏提示文案，避免未封存新段 revision 导致界面长期显示“等待上传”**（P1）。

完成这三处调整后，后台队列即可安全支撑后续的 IndexedDB/恢复与自适应界面的对接。
