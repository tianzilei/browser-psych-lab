### 2. 通用 Condition 隐藏题“脏值复活”推导与修正

你推演的链路在当前代码中**完全成立**，且精准指出了客户端本地状态重建与服务端权威归一化之间的脱节。

#### A. 逐步代码定位与成立分析

1. **未封存段本地快照写入**： 在 `adaptive-page.ts` 的 `forward` 触发完成时：`// adaptive-page.ts
const checked = pageSnapshot(page, preceding, data);
await api.ledger.append(page.id, 'PAGE_SNAPSHOT', { answers: data }, [...path, page.id], data);`此处传入 `append` 的第四个参数 `pageValues` 是未归一化的原始 `data`（保留了 `H: "foo"`）。
2. **刷新时的初始化合并**： 在 `adaptive-survey.ts` 重新挂载时：`// adaptive-survey.ts: 第 13 行
const answers: Record<string, Answer> = { ...api.session.answers };
for (const page of protocol.pages) Object.assign(answers, local.page_values[page.id] ?? {});`由于段 1 尚未 seal，`api.session.answers`（服务端状态）中没有段 1 的数据。代码直接将 `local.page_values[page.id]`（包含 `H: "foo"`）浅拷贝并覆盖进 `answers`。`H` 确实在此处发生“脏值复活”。
3. **客户端错误的后段推演**： `show()` 运行时：
  - 段 1 在 `local.pending` 中，被跳过；
  - 推进到段 2 时，`evaluate(page2.condition, answers)` 使用了包含 `H: "foo"` 的脏 `answers`，导致客户端判定段 2 条件成立并挂载展示。受试者在段 2 输入并生成了 `PAGE_REVISION`。
4. **服务端权威归一化与哈希链冲突**： 后台连接恢复，`upload()` 先同步并调用 `api.seal(page1.id)`。 服务端处理段 1 seal 时，运行 `pageSnapshot` 并将 `H` 归一化为 `null`；紧接着服务端执行 `skipPages()`，由于 `answers.H === null`，服务端将 `page_index` **直接跳过段 2**，推进到了段 3（或更新了跳转后的 `path`）。 **后果**：客户端本地 IDB 中此时已经记录了段 2 的事件，且后续若段 2 拍快照，其 `manifest.path` 包含了 `[...path, page2.id]`，而服务端的预期路径已经越过了段 2。这会导致客户端本地的预期路径与服务端计算的权威路径出现永久性分歧，直接触发 **`SEAL_MISMATCH` 或服务端 Scope Quarantine**。

#### B. 影响范围

- **当前三份长问卷**：完全无条件跳转（无 condition），故**不会触碰此路径**。
- **通用 Adaptive 问卷**：只要存在跨段条件依赖，并在未 seal 状态下发生刷新重入，即有确定概率破坏后续段的状态机同步。

#### C. 最小代码级修复方案

在 `adaptive-survey.ts` 初始化挂载以及断点恢复构建全局 `answers` 时，**严禁对未 seal 的 pending 段直接使用未加工的 `page_values`**，必须经过 `pageSnapshot` 规范化投影后再合入：

```
// src/web/adaptive-survey.ts: 替换原 13 行附近的 answers 组装逻辑
const answers: Record<string, Answer> = { ...api.session.answers };
for (const page of protocol.pages) {
  // 1. 已由服务器 seal 的段，直接以服务端返回的权威 answers 为准（此处已有）
  if (api.session.seals.some(s => s.manifest.scope === page.id)) continue;

  // 2. 本地已生成 snapshot 处于 pending 状态的段，按 pageSnapshot 重新计算规范化答案
  const values = local.page_values[page.id];
  if (values && local.pending[page.id]) {
    const preceding = { ...answers };
    for (const q of page.questions) delete preceding[q.id];
    const normalized = pageSnapshot(page, preceding, values);
    for (const [id, v] of Object.entries(normalized)) answers[id] = v.answer;
  } else if (values) {
    // 3. 仅处于正在作答（未 snapshot）状态的当前段，合并本地草稿供当前段恢复
    Object.assign(answers, values);
  }
}
```

#### D. 关键回归测试用例（静态设计）

- **用例设计**：构造包含跨段依赖的协议（段 1 题 A=yes 触发题 H；段 2 仅在 H!=null 时展示）。在段 1 填写 A=yes, H=foo 后回退将 A 改为 no。完成段 1 并生成本地 snapshot，在触发网络 seal 前断网并刷新页面。
- **验证点**：页面刷新后，客户端计算段 2 时必须判定其条件为 false 并自动跳过；联网恢复后，段 1 正常 seal，服务端与客户端推进到的下一可用 `page_index` 严格一致，无路径分歧。

### 3. 事件与数据量预算修正

- **核实更正**：撤回上一轮“每段最多 30 条 revision + 1 snapshot”的定论。
- **实际机制**：由于 `PAGE_REVISION` 会随用户的每次有效修改（如文本框逐字输入、选项来回切换更正）持续调用 `append` 写入 IDB，单段内的事件总数是动态累加的。
- **风险边界**：系统受限于单 scope 5000 事件及 32MiB 的硬上限。尽管在正常作答情况下（三份问卷以 1~5 单选量表为主，仅首题为 15 位数字文本），单段 30 题很难在常规作答中产生数千次修改，但在极端场景下（如受试者长时间在单段内频繁反复更改选项，或脚本化高频触发），依然存在逼近或触发 5000 事件限制的可能。
- **工程应对**：不能从理论上推定其绝对不超限，针对长耗时反复编辑的极限场景，需补足异常高频修改下的事件计数与空间耗尽拦截测试。
