# 会话排队与 1c2g 部署

2026-10-08。用户将需求调整为整个研究同时进行 1–2 例，其余等待。当前实现默认 2 例，可配置为 1；图片准备保持单流。此要求覆盖此前“20 人同时采集”的容量目标。20 人仍可作为集中到达的排队测试人数。

## 配置与占位范围

在受保护的部署环境文件中设置：

```dotenv
SESSION_CONCURRENCY=2
PREPARATION_CONCURRENCY=1
```

`SESSION_CONCURRENCY` 只接受整数 1 或 2，默认 2；其他值使服务启动失败。1c2g 初次试运行建议先设为 1，完成实际负载验收后可改为 2。配置作用于单个应用内所有研究的合计例数，应用仍只有一个 HTTP 进程和一个 DB writer。不要通过启动两个应用进程实现两例并行。

会话从放行开始占位，覆盖问卷作答、图片准备、等待开始、图片组执行、补传封存及最终完成。图片准备另有 FIFO 队列，默认一个图片流；两例并行不等于两路同时下载。超过会话名额的人显示等待位置，尚不显示问卷、不领取写者和运行许可；直接调用开始接口同样会被服务端拒绝。

| 情况 | 队列行为 |
| --- | --- |
| 正常完成或明确终止 | 释放会话名额，按 FIFO 放行下一例 |
| 刷新、问卷与图片页切换 | 复用会话及有效排队序位，更新票据；旧页面迟到释放不影响新票据 |
| 点击“退出等待” | 精确释放当前票据；重新加入排在队尾 |
| 排队或准备/问卷阶段失联 | 没有未关闭许可时，5 分钟租约到期回收；原始记录、答案、会话身份和已分配方案保留，重连重新入队 |
| 图片运行许可仍为 ISSUED | 持续占位，不依赖租约、页面可见性或进程存活；恢复页面需明确确认旧运行中断并终止 UNKNOWN |
| 升级或从 2 例改为 1 例时已有更多占位 | 保留已有占位，不强制终止；排队停止新增放行，直到占位数降到新上限以下 |

会话队列包含最多 64 个有效条目（活动与等待合计），满时返回 `SESSION_QUEUE_FULL`。队首约 3 秒、其他等待者约 10 秒查询一次，附少量随机抖动；活动会话每 60 秒续租。相同票据的租约更新合并为最多每分钟一次，降低 SQLite 写入频率。会话队列没有固定总等待时长，保持连接即可继续等待；图片准备自身仍保留原来的有限超时预算。

开始计时图片组前停止所有续租与准备轮询，等待在途请求结束；服务端已发许可负责占位，组内保持零 HTTP。第二标签页受浏览器独占锁保护，只读且不更换活动页票据。票据是操作层防迟到保护，原有写者 fence、Cookie 鉴权和运行许可检查继续执行。

## 持久性与运维

会话队列使用新的 SQLite 操作表 `lab_session_queue`，队列检查和业务放行都在唯一 writer 的短事务内完成。排队拒绝在事务提交后返回 409，入队状态不会因业务被拒而回滚。原 `lab_sessions` 生命周期和原始事件、凭证、封存、冻结版本保持原合同。历史补传与对账继续可用，补传本身不允许等待者开启新任务。

SQLite 重启/备份恢复保留有效 FIFO 序位；超过租约且没有 ISSUED 的条目会在后续查询中清理。图片准备票据仍在内存中，重启后重新准备。升级时已有的 ISSUED 会话自动补入活动占位；不能为了排队进度自动将未知运行判断为成功或空闲。

管理页“运行状态”的 `state.admission` 显示 active、queued、limit、capacity、pinned、over_limit；`preparation` 单独显示图片流队列。`lab_sessions.state=ACTIVE` 不等于持有参加名额，应结合 admission 查看。计划调低并行数时优先等待当前例次结束；配置变更需要重启，既有未知许可继续占位。

## 1c2g / 1Mbps 的部署起点

1c2g 可作为单例先行、最多双例的试运行候选，实际容量尚未在用户 ECS 测量。构建、浏览器检查和依赖准备在开发/构建机器执行，服务器只运行构建产物、生产依赖、nginx 与备份入口。

原 [systemd 模板](../deploy/browser-psych-lab.service) 的 `MemoryMax=1536M` 面向此前 2c4g 配置。提供可选 [1c2g drop-in](../deploy/1c2g.conf)：

```ini
[Service]
Environment=UV_THREADPOOL_SIZE=1
MemoryMax=1024M
```

将其放到 `/etc/systemd/system/browser-psych-lab.service.d/1c2g.conf`，同时在 `/etc/browser-psych-lab.env` 中设 `SESSION_CONCURRENCY=1`、`PREPARATION_CONCURRENCY=1`，再按 [部署手册](部署与恢复手册.md)安装发行物和 HTTPS 配置。1024M 是待实测的应用 cgroup 上限，并非内存需求预测；它包含该服务的 worker 等进程占用。检查实际 RSS、CPU、OOM、WAL/FULL 提交尾延迟和等待耗时后再决定是否放开双例。

1Mbps 是整个服务共享的出站预算；排队不能增加总带宽。公共代码、问卷、API、管理预览和导出下载仍占带宽。采集期间错开大文件下载、集中预览及重建，备份按所需 RPO 继续安排。总耗时取决于各例实际作答时间和原图字节量，尚不能承诺等待时长。

## 本机验证与边界

- `npm run check`：TypeScript、构建/预压缩、SQLite smoke、52 项单元及故障测试、19 项 Chromium 测试通过。
- 单元测试覆盖单例/双例服务端门控、完成与终止放行、刷新票据和迟到释放、有限容量、无变化轮询不写入、SQLite 重启序位、失联清理和未关闭许可跨租约占位。
- 浏览器覆盖两例作答、第三/第四例等待且没有 writer、刷新保持次序、主动退出重排、完成放行、第二标签只读、原零 HTTP 图片组和离线原字节恢复。
- [双例混合报告](混合采集本机测量.json)、[单例混合报告](单例排队本机测量.json)：1/5/10/20 个集中到达波次，实际活动例数受 2/1 上限约束，使用合成软件记录和真实 HTTP/SQLite/图片解码/重放/CSV/备份。
- [1Mbps 限速报告](1Mbps排队本机测量.json)：20 个会话先排整例队列，再排单路图片准备；下载后以 TEST_ONLY 原因终止释放名额，不执行真实试次。

```sh
nvm use
npm run check
npm run doctor
npm run profile:mixed -- docs/混合采集本机测量.json
SESSION_CONCURRENCY=1 npm run profile:mixed -- docs/单例排队本机测量.json

```

测量在 macOS / Apple M4 上运行，等待轮询使用脚本固定 1 秒；限速只统计 loopback HTTP 累计响应正文 125000 B/s，排除头部、TLS 和实际 ECS 的 CPU/磁盘/网络限制。它们验证排队逻辑与数据合同，不能替代真实 1c2g/2c4g、真实设备或独立恢复验收。正式 gate 保持关闭。
