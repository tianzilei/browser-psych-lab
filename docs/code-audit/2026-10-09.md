## 已确认的问题

### A01 · P2 · 左右键组合操作会丢失下一次作答
位置：src/web/runner-input.ts:15；src/web/run.ts:77；src/shared/run-replay.ts:82。

触发：左键按下 → 右键按下 → 左键释放 → 右键释放。Chromium 将中间的按钮变化作为 pointermove，最终发送 button=2 的 pointerup。绑定器只监听 pointerdown/up/cancel，并忽略非主键事件，因此仅记录 down，回放器的 pointers 集合残留。下一次正常左键按下被当成仍在长按而拒绝；这次点击的 up 才清除残留。键盘作答也会被残留指针阻止。并非永久锁死。

证据：真实 Chromium 事件经实际 bindRunnerInput 生成记录，送入 RunReplay；两次 down 的有效性为 [true,false]，第二次 up 后 pointers.size=0。修复建议：按 buttons 位掩码识别主键释放，处理 pointermove 中的按钮转换，并覆盖取消/失焦释放；右键仍不得产生作答。

### A02 · P2 · 合法保存预算超过固定的首刺激准备时间
位置：src/server/lab-store.ts:436；src/shared/protocol.ts:139；src/shared/scheduler.ts:76。

协议允许 commit_ms=1000、activate_ms=10、margin_ms=10，但 permit 固定 start=1000。运行器从本地 origin 计时并开始 stage；即使 stage 在 0ms 完成调用，1020ms 的所需预算也超过 1000ms，必定抛出 COMMIT_DEADLINE_UNSAFE。这里不是网络往返时间的问题。

证据：parseProtocol 接受配置，Scheduler.stage('first',0,...) 立即终止。修复建议：首刺激目标由完整预算加准备余量导出，或在发布前拒绝不可能执行的预算；明确保持组内时钟语义。

### A03 · P2 · 短静态试次能发布，但准备下一题时立即中断
位置：src/shared/protocol.ts:166；src/web/run.ts:101；src/web/run.ts:73。

协议只在 repeats>0 时检查 ISI 预算。repeats=0、两题各 image_ms=10 / isi_ms=0 合法；60Hz 帧量化后单题为约16.67ms。运行器在第一题 ONSET 时才 stage 第二题，而默认提交/激活/余量共60ms，剩余16.67ms不足，抛出 COMMIT_DEADLINE_UNSAFE，中断该组。

证据：实际 parseProtocol、realizeTrials（60Hz）和 Scheduler 的组合复现，第二目标1016.67ms、准备时点1000ms。修复建议：静态模式也校验可用准备间隔；若需要一帧刺激，应重新设计提前准备队列，不能简单降低持久化保证。

### A04 · P2 · 崩溃遗留锁遇到 PID 复用时阻止服务重启
位置：src/server/db-worker.ts:16。

数据库持有者只保存 pid/随机 owner；owner 不同就用 process.kill(pid,0) 判断进程是否还活着。崩溃或重启后 PID 被无关进程复用时，存活不代表仍有该数据库的持有者，但代码始终抛出 DATABASE_ALREADY_OWNED，阻止启动。

证据：临时数据库中注入“旧 owner + 存活但不持有数据库的审计进程 PID”，实际 DatabaseWriter.start 拒绝。此证据模拟 PID 复用后的状态，不声称自然触发了系统 PID 复用。修复建议：将进程启动身份/主机启动标识纳入验证，或使用平台提供的进程生命周期锁；不能简单删除存活进程锁而破坏单写者保护。

### A05 · P2 · 局域网预览 HTTP 入口可因畸形 URL 退出
位置：scripts/preview-questionnaire.mjs:40。

使用 --lan 时重定向服务器监听 0.0.0.0，回调直接执行 new URL(request.url,origin)。HTTP 请求目标为 http://[ 时 Node HTTP 层接受请求，但 URL 构造抛出 ERR_INVALID_URL；没有捕获，整个预览进程退出，同进程 HTTPS 预览也随之中断。

证据：从源码提取原样 HTTP 回调，在隔离子进程与临时端口发送原始请求，进程以1退出并输出 ERR_INVALID_URL。未启动完整 POSIX 预览部署。修复建议：捕获 URL 解析错误并返回400，必要时只接受应用支持的请求目标格式。影响限于局域网预览脚本，不扩大到 Fastify 生产路由。

### A06 · P3 · CSV 导出清单漏计 asset_refs 数据行
位置：src/server/maintenance-worker.ts:158。

导出末尾总会 emit 一条 asset_refs CSV 记录（即使引用为空也是 []），却没有增加 rows，也没有记录 tables.asset_refs。因此 manifest.rows 比实际 CSV 数据记录数少1（不计表头），基于清单进行行数核对会失败。这一行的 source.update 还使用了不同编码格式；目前没有消费者要求统一格式，故不单独宣称摘要无效。

证据：完整 EXPORT 控制流静态确认。当前 Windows 的私有存储前置检查阻止完整导出集成测试，本项未声称端到端复现。修复建议：使用统一的“写记录并计数”函数，更新清单并用 CSV 解析器核对记录数，避免按物理换行统计含多行字段的 CSV。
